# Migración relacional a SQL Server 2025

`backend/cmd/migrate-relational-data` transfiere una copia congelada de PostgreSQL a una base SQL Server nueva. MongoDB conserva sus datos e identificadores. El comando inspecciona una copia de MongoDB y valida que sus referencias existan en ambos motores relacionales.

## Preparación de un ensayo privado

1. Durante una ventana aprobada, bloquea las escrituras de la aplicación y de cualquier integrador. Obtén respaldos recuperables de PostgreSQL y MongoDB en el mismo punto de corte. Incluye las cuatro colecciones técnicas, los binarios de GridFS y el estado de las secuencias. Registra hashes y verifica la restauración en un entorno privado.
2. Restaura PostgreSQL como `elbravodeljac_pg_migration` y MongoDB como `elbravodeljac_tecnico_migration`. Restringe las cuentas de lectura a las copias y no habilites aplicaciones que puedan escribir en ellas. Las secuencias de PostgreSQL quedan fuera de la instantánea transaccional, por lo que tampoco debe haber escritores que las consuman. La cuenta de origen requiere `SELECT` sobre las tablas y secuencias. La de MongoDB requiere lectura sobre el marcador y las colecciones técnicas.
3. Crea `elbravodeljac_sqlserver_migration` en SQL Server 2025, con compatibilidad 170. Aplica [el esquema físico](esquema_entrega.sql) con `sqlcmd -b -f 65001`. Mantén las 28 tablas vacías. La cuenta temporal de destino necesita leer e insertar en el esquema, y permiso para administrar sus claves foráneas, triggers y secuencias. No ejecutes el bootstrap de usuarios ni los fixtures de pruebas.
4. Genera un marcador aleatorio de 32 bytes en hexadecimal. Desde las cuentas de preparación, asocia ese valor con el comentario de la base PostgreSQL, la propiedad extendida de base `jac.migration_run` en SQL Server y un documento con ese valor como `_id` en `migration_control` de la copia MongoDB. El [workflow](../../.github/workflows/relational-data-migration-qa.yml) muestra cómo hacerlo en un entorno desechable. Los tres servicios deben estar accesibles por loopback y puertos explícitos.
5. Pasa el marcador y las tres conexiones mediante el gestor privado de secretos o variables del proceso. El comando recibe `MIGRATION_RUN_TOKEN`, `MIGRATION_POSTGRES_DSN` (`postgres://`), `MIGRATION_SQLSERVER_DSN` (`sqlserver://` con `database`) y `MIGRATION_MONGODB_URI` (`mongodb://` con el nombre de base y `directConnection=true`). Usa el TLS y las credenciales de las copias. Desde `backend`, ejecuta `go run ./cmd/migrate-relational-data`. `MIGRATION_TIMEOUT` admite una duración como `30m`. No registres las cadenas de conexión.

## Qué se verifica antes de confirmar

- Coinciden los nombres de tablas y columnas, los tipos compatibles, las 28 claves primarias y las 50 relaciones. Se copian los valores de las 208 columnas, incluso IDs de tablas puente, hashes de credenciales, autores, estados, importes y snapshots. Se relee cada tabla por su clave primaria y se verifica el conteo y un SHA-256 que distingue nulos de valores vacíos y conserva la representación decimal, Unicode, JSON y binaria. Las fechas se comparan por instante UTC con precisión de microsegundos.
- El destino se bloquea y se comprueba vacío. Durante la transacción solo se suspenden los triggers de escritura y las FK del destino para conservar registros históricos y cargar relaciones en cualquier orden. PK, índices únicos y `CHECK` siguen activos. Las FK se revalidan sobre todos los datos con `WITH CHECK CHECK` y los triggers se reactivan antes de confirmar. La comparación incluye el importe efectivo, pagos netos y saldo por orden.
- Cada secuencia reinicia en el mayor de dos valores, el próximo valor reservado por PostgreSQL o la mayor PK importada más uno. La comparación comprueba que los IDs de diagnóstico y autor existan en ambos motores. Verifica además los vínculos GridFS, longitud y SHA-256 del archivo, y rechaza evidencias pendientes, archivos o fragmentos huérfanos. El comando no altera MongoDB.
- El informe muestra solo conteos. Un fallo aborta la transacción. Ante pérdida de conexión al confirmar, no supongas el resultado ni repitas sobre ese destino. Conserva los respaldos, comprueba el estado y prepara otra base vacía.

## Revisión antes de un cambio real

El ensayo de GitHub Actions usa datos sintéticos. Para datos reales se necesita una ejecución privada sobre una copia representativa, una medición de tiempo, espacio y log transaccional, y una conciliación con los respaldos y los sistemas consumidores. Nunca se transfieren datos reales ni copias a CI.

SQL Server puede considerar iguales claves que PostgreSQL distingue por espacios finales. También pueden fallar fechas fuera del rango de `datetimeoffset`, valores incompatibles con los `CHECK` del destino o evidencia técnica inconclusa. Investiga esas diferencias en la copia y acuerda el tratamiento con el responsable de los datos. El comando no trunca, deduplica, reasigna IDs ni corrige historiales automáticamente.

En la ventana de cambio, toma un corte fresco con todas las escrituras bloqueadas y repite la carga. Revisa los conteos, los saldos, los próximos IDs, las sesiones, los roles, las fichas y una muestra de evidencias. Para conectar la API, restaura el destino verificado bajo el nombre de base admitido por su configuración y revalida antes de habilitar escrituras. Conserva PostgreSQL y MongoDB habituales y sus respaldos. Antes de la primera escritura en SQL Server se puede volver a la configuración anterior. Si SQL Server ya recibió cambios, congela ambos lados y concilia esas escrituras antes de volver a PostgreSQL.
